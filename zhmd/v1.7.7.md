## 概述
修复 **Anima**（尤其是 **`AnimaWai68`** / `waiANIMA_pw3.safetensors` 等 68 通道权重）在主图 **txt2img** 成功后，**ADetailer** 对每个检测区域做 **img2img** 后处理时崩溃的问题。
主生成正常；ADetailer 在第二次 img2img 阶段报错：
```text
RuntimeError: Tensors must have same number of dimensions: got 4 and 5
```
典型堆栈位于 `modules/processing.py` 的 `inpainting_image_conditioning`，在 `torch.cat([conditioning_mask, conditioning_image], dim=1)` 处失败。
**提交：** `9c85472` — `fix-Anima-ADetailer-disable-WebUI-inpaint-concat`  
**改动范围：** 仅 `backend/diffusion_engine/anima.py` 中 `Anima` 引擎类（与 Qwen / Flux / Lumina 等已有做法一致）。

---

## 现象
| 项目 | 说明 |
|------|------|
| **何时失败** | 主 **txt2img** 完成；**ADetailer** 对每个检测框启动 **img2img** 精炼时 |
| **错误** | `Tensors must have same number of dimensions: got 4 and 5` |
| **常见模型** | `waiANIMA_pw3.safetensors`（识别为 `AnimaWai68`，`in_channels: 68`） |
| **扩展** | 内置 **ADetailer**（`extensions-builtin/adetailer`） |

---

## 原因（简要）

### 1. `AnimaWai68` 被误判为「inpaint 模型」
`modules_forge/packages/huggingface_guess/model_list.py` 中：
```python
def inpaint_model(self):
    return self.unet_config.get("in_channels", -1) > 4
```
`AnimaWai68` 的 `in_channels` 为 **68**（架构输入宽度），故 `68 > 4` → **`inpaint_model()` 为 True**。  
加载后 `ForgeDiffusionEngine` 会把 **`self.is_inpaint = True`** 写入引擎。
对经典 **SD inpaint** 检查点，这表示 UNet 需要 mask+image 通道拼接；对 **Anima**，68 通道描述的是 **Wan/Anima 架构本身**，并不表示应走 WebUI 的 SD 式 latent 拼接路径。

### 2. ADetailer 始终带 mask 做 img2img
ADetailer 为每个检测区域构造 `StableDiffusionProcessingImg2Img`，设置 `image_mask` 并调用 `process_images()`。即使用户未在主任务中手动启用 inpaint，后处理仍是 **带 mask 的 img2img**。

### 3. `is_inpaint=True` 走错分支
`img2img_image_conditioning()` 在 `self.sd_model.is_inpaint` 为 True 时调用 **`inpainting_image_conditioning()`**（SD 1.x / SDXL 传统 inpaint 路径）：
- 将 mask 与编码后的图像 latent 在通道维 **concat** 后送入 UNet。
- 该路径假定 latent 为 **4D** `(B, C, H, W)`。
**Anima** 使用 **Wan VAE**，编码结果为 **5D** `(B, C, T, H, W)`（含时间/帧轴 `T`，即使 `T=1`）。  
mask 侧经插值与 expand 后多为 **4D**，与 **5D** 的 `conditioning_image` 在 `torch.cat` 时维度不一致 → 崩溃。

### 4. Forge 已有 5D mask 混合，与 concat 路径冲突
同一 `StableDiffusionProcessingImg2Img.init()` 中，当 `init_latent` 为 5D 时，会把 `mask` / `nmask` 扩展为 5D；`sample()` 内用 **latent 混合**（`samples * nmask + init_latent * mask`）处理区域 mask。  
**问题不在「Anima 不能 inpaint」**，而是 **`is_inpaint` 标志错误** 导致走了不兼容 5D 的 **legacy concat** 分支。

### 5. 其他引擎已规避，Anima 此前缺失
Qwen、Lumina、Flux、Chroma、ZImage 等在 `__init__` 里均在 `super().__init__()` 之后设置 **`self.is_inpaint = False`**。**Anima** 此前未覆盖，故仅 Anima（尤其 68 通道）在 ADetailer 场景下触发此 bug。

---

## 修复内容
**文件：** `backend/diffusion_engine/anima.py`  
**类：** `Anima`（`matched_guesses`: `Anima`, `AnimaBase`, `AnimaWai68`）
在 `Anima.__init__` 中，`super().__init__(...)` 之后增加一行：
```python
self.is_inpaint = False
```

### 修复后的行为
| 项目 | 说明 |
|------|------|
| **不再调用** | `inpainting_image_conditioning()` 中的 4D/5D `torch.cat` |
| **`image_conditioning`** | 走 `img2img_image_conditioning()` 的 **dummy** 分支（与 Qwen/Flux 等一致） |
| **区域 mask** | 仍由 `init()` 扩展 5D mask，在 `sample()` 中 **latent 混合** 生效 |
| **ADetailer** | 每个检测区域的 img2img 可正常完成 |

### 未改动的部分
| 区域 | 说明 |
|------|------|
| SD1 / SDXL / 真实 inpaint 检查点 | 仍使用 `base.py` 默认 `is_inpaint` |
| `modules/processing.py` | 无全局修改 |
| `huggingface_guess` / `AnimaWai68` 配置 | `in_channels: 68` 不变 |
| Anima UNet、VAE、文本编码器 | 无改动 |
| 主 txt2img | 行为不变 |

## 设计要点
- **`in_channels > 4`** 在 `huggingface_guess` 中表示「UNet 输入通道数大于 4」；对经典 SD 可推断 inpaint concat，对 **AnimaWai68** 则表示 **模型架构**，不能等同 WebUI inpaint 语义。
- Forge 上 flow/Wan 类引擎的推荐模式：**引擎侧 `is_inpaint = False`** + **img2img `sample()` 中的 mask 混合**。
- 本修复使 **Anima** 与 Qwen、Lumina、Flux、Chroma、ZImage 采用同一模式，**仅作用于 Anima 引擎实例**，不影响其他模型。
